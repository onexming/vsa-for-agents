# 功能切片工作规范

本文件是单交付单元项目的目标蓝图、全局职责、领域与功能切片内部结构，以及新增、修改、移动、拆分或审查切片流程的唯一权威来源。每次功能工作都先建立全局坐标，再进入具体切片。

文件名和示例使用 Python 风格表达语义，不要求其他语言复制其语法或运行模型。尖括号表示由语言生态和工具链决定的职责映射，不要求逐字使用示例名称。

## 目标蓝图

```text
<repository>/
├── AGENTS.md                              # Agent 规则与渐进式路由
├── README.*                               # 项目目的、运行和验证入口
├── <toolchain-files>                      # 构建、依赖和语言工具配置
├── docs/
│   └── architecture/
│       ├── feature-work.md                # 本蓝图及切片规范的权威来源
│       ├── ...                            # 其他专题架构规范
│       └── decisions/                     # 有架构决定时出现
├── <source-root>/
│   ├── features/
│   │   ├── <domain>/
│   │   │   ├── _shared/                   # 有真实领域共享时出现
│   │   │   └── <verb-object>/             # 一个完整行为
│   │   └── <another-domain>/
│   ├── shared/                            # 有跨领域纯技术复用时出现
│   ├── composition/                       # 注册和装配；可映射为文件
│   └── <application-entry>.*              # 交付单元启动入口
├── <automation>/                          # 按需：项目自动化
├── <deployment>/                          # 按需：部署资产
└── <ci-config>/                           # 按需：持续集成配置
```

蓝图描述规范性目标结构，不是目录初始化清单。职责可以由单个文件承担；只在有真实内容时建立按需区域，不为匹配蓝图创建空目录，也不借功能任务初始化无关区域。

本蓝图不定义多交付单元目录结构。任务涉及不同交付单元之间的协作时，读取 [`cross-boundary-communication.md`](cross-boundary-communication.md)。

## 全局职责

- `AGENTS.md` 保存常驻规则和任务路由；架构细节由其指向的专题文件维护。
- `README.*` 给出项目用途，以及工具链中实际存在的构建、运行和验证入口，不复制工具配置。
- `<toolchain-files>` 是依赖、构建、格式、静态检查和测试命令的环境事实来源。
- `docs/architecture/` 保存架构规范和决策，不承载生产业务实现。
- `<source-root>/features/` 保存全部业务语义，先按领域、再按用户意图组织。
- `<source-root>/shared/` 只保存无业务语义的技术基础设施；提升条件见 [`shared-code.md`](shared-code.md)。
- `<source-root>/composition/` 只负责发现、注册、装配和启动；它可以是目录，也可以由入口附近的单个文件承担。
- `<application-entry>.*` 是交付单元启动入口，不在其中实现业务规则。
- `<automation>`、`<deployment>` 和 `<ci-config>` 分别容纳自动化、部署与持续集成资产；名称和位置服从工具链。

新增、修改、移动或审查测试及其配套环境文件时，完整读取 [`test-placement.md`](test-placement.md)；建立共享模块、跨边界协作或平台强制目录时，分别读取 [`shared-code.md`](shared-code.md)、[`cross-boundary-communication.md`](cross-boundary-communication.md) 和 [`exceptions.md`](exceptions.md)。

## 切片边界

- 领域是一组具有共同业务语言的能力，不以数据库表或框架模块命名。
- 功能切片表达一个用户意图、业务命令、查询或外部事件处理目标。

一个合格切片必须同时具备明确意图、可识别的公共入口、完成行为所需的私有实现、可观察结果，以及无需读取其他切片内部代码即可理解和测试的边界。切片不是单个函数、接口或数据库实体。

## 切片内部结构

```text
features/<domain>/
├── _shared/                         # 提升规则见 shared-code.md
├── <verb-object>/                   # 一个完整行为
│   ├── <entry>.*                    # HTTP、RPC、CLI、UI、消息、任务等入口
│   ├── <contracts>.*                # 输入、输出和错误契约
│   └── <implementation>.*           # 流程、状态变化和私有适配
└── <another-verb-object>/
```

目录表达边界，不规定固定文件清单。简单切片可以只有实现文件；复杂切片可以在自身目录内按入口、契约、流程、展示、查询或持久化适配继续拆分。

## 命名与职责

- 领域使用业务名词；单复数和大小写遵循项目及语言约定，同一作用域保持一致。
- 切片使用表达意图的“动词 + 对象或结果”，例如 `create_order`、`approve_order`、`get_order_detail`。
- 切片专属的契约、流程、数据访问、映射、展示和适配保留在切片目录。
- 统一的 `controllers/`、`services/`、`repositories/`、`components/` 或 `stores/` 不得成为全部业务代码的横向归宿。
- 聚合创建、取消、审批等多个意图的 `Service`、`Manager`、`Processor` 或 `Coordinator` 应拆成独立切片。

## 新增功能流程

1. **建立全局坐标。** 确认仓库根、源码根、现有全局职责和目标领域；新行为在蓝图中的唯一位置明确时完成。
2. **确定意图边界。** 输入、结果或失败分支可独立变化时创建新切片；切片名称能唯一表达行为时完成。
3. **定义公共契约。** 明确入口、输入、输出、错误和可观察结果；契约不暴露框架请求对象或内部持久化模型时完成。
4. **实现完整路径。** 校验、业务决策、状态访问、映射、展示和私有适配均位于切片内；未产生跨切片内部依赖时完成。
5. **显式装配。** 在组合根注册入口并绑定运行时依赖；注册不依赖隐式导入副作用且组合根无业务判断时完成。
6. **从入口验证。** 覆盖成功路径、主要失败路径、边界条件及状态、事件、消息、文件或界面等结果；按 [`test-placement.md`](test-placement.md) 放置测试，相关测试通过时完成。
7. **验证边界。** 更新并运行可用的架构依赖检查、模块边界测试和静态检查；没有自动化检查时，逐条记录依赖方向的代码审查结论。确认违规为零时完成。

## 修改已有功能流程

1. 先在目标蓝图中定位该行为对应的唯一领域、切片、公共入口、组合关系和相关测试。
2. 枚举可能变化的输入、输出、错误、事件和调用方兼容性。
3. 将大部分修改限制在该切片内；若必须触及多个无关切片，先检查通信契约或领域边界是否错误。
4. 消除新增或暴露出的跨切片内部依赖。需要提取共享内容时读取 [`shared-code.md`](shared-code.md)；需要跨边界协作时读取 [`cross-boundary-communication.md`](cross-boundary-communication.md)。
5. 保持组合根只做装配，并从公共入口验证所有改变的可观察结果。

## 资源与平台映射

- 带业务语义的手写资源就近归属相应切片。
- 跨领域且无业务语义的资源进入对应技术共享区域。
- 工具强制目录和生成物遵循语言与平台约定；若强制位置影响业务边界，读取 [`exceptions.md`](exceptions.md)。
- 服务端、客户端、CLI、桌面、批处理和设备程序可以使用不同入口与资源目录，但必须保留相同职责映射。

## 拆分判定

出现多个独立输入、可分别失败或重试的流程、对应不同用户意图的大量条件分支、不相关结果或互不相关的测试场景组时，读取 [`edge-cases.md`](edge-cases.md) 并按意图或业务结果拆分。文件数量只是审查信号，不是机械边界。

## 完成标准

- 每个现有目录具有唯一职责，业务代码可以沿“源码根 → 领域 → 用户意图”定位。
- 所有按需区域都有真实内容，不存在仅为匹配蓝图而创建的空目录。
- 修改单个行为时，大部分变化落在一个切片目录。
- 公共入口、可观察结果及完整行为测试齐备，私有实现未被其他切片引用。
- 共享代码逐级提升，全局共享不含业务语义。
- 组合根只装配；工具、资源、部署及生成目录不承载隐藏业务规则。
- 实际名称即使不同，也能完整映射到蓝图职责；框架或部署变化不会改变业务边界。
