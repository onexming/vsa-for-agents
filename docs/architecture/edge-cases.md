# 架构边界复合判断

本文件只处理单一主流程无法可靠决定的复合情形。得到结论后，实施与验证仍回到对应专题规范。

## 跨领域出现相似校验

按以下顺序判断：

1. UUID、邮箱语法、编码格式等纯技术校验，按 [`shared-code.md`](shared-code.md) 评估全局技术共享。
2. 最低订单金额、提现额度等领域规则由各领域分别拥有；相似代码不是共同概念。
3. 只有业务语言确认二者属于同一更高层概念时，才重新划分领域或建立公开能力。
4. 需要读取状态或产生副作用时，它是行为，不是共享函数；建立切片或公开协议。

完成条件：规则所有者、业务含义和目标边界均唯一明确，而不是仅依据代码形状决定。

## 切片持续膨胀

出现以下两项或存在一项强信号时，重新划分意图边界：

- 多个完全不同的输入或触发入口。
- 可以分别失败、重试或部署的子流程。
- 大量条件分支对应不同用户意图。
- 同时产生多种不相关结果。
- 测试自然分成互不相关的场景组。
- 修改一个分支经常影响无关分支。

按用户意图或业务结果拆分，而不是按文件类型或文件数量拆分。文件超过 6～8 个只是审查信号。两个候选切片若总是同步变化，反向检查它们是否其实属于同一行为或当前领域边界是否错误。

完成条件：每个结果切片都有单一意图、独立公共入口、可观察结果和完整行为测试。

## 高扇入领域共享

一个 `_shared/` 模块被五个以上切片引用时，依次检查：

1. 它是否只是稳定而简单的模型、值对象、错误、事件或纯规则。
2. 是否出现副作用、流程编排、大量可选参数或场景标志。
3. 是否聚合多个主动行为并以 Service、Manager 等名称持续增长。
4. 高扇入是否说明领域过大，或多个所谓切片其实属于一个更高层行为。

稳定被动定义可以继续共享；主动行为拆为切片；领域过大时重新划分边界。完成条件是保留部分可以独立理解、无副作用且不驱动任何切片。
