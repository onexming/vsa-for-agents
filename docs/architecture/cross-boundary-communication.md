# 跨边界通信规范

本文件是设计或修改切片间、领域间及交付单元间协作时的权威流程。

## 基本边界

切片内部文件默认私有。调用方不得依赖另一个切片的处理函数、内部模型、私有校验、仓储实现或目录结构。跨边界协作只能选择以下方式之一，并将连接关系显式装配。

## 允许方式

### 共同依赖全局技术基础设施

多个切片可以共同依赖 `shared/` 中的时钟、事件总线、传输、日志等无业务语义能力。`shared/` 不得转发业务调用或成为服务定位器。

### 发布领域事件或消息

一个行为完成后触发通知、审计、同步、索引或异步处理时，由生产切片发布具有稳定载荷的事件，由独立消费切片订阅。订阅关系在组合根中注册；生产者不导入消费者，消费者不依赖生产者内部实现。

事件契约由能力提供方或独立协议包维护。业务事实使用过去式语义；载荷只包含订阅方所需的公开数据。

### 调用公开协议或进程边界

同步读取其他领域数据或调用其他交付单元时，使用公开 API、RPC、请求消息或等价协议。调用方为公开响应建立本地契约或依赖独立 Schema，不导入提供方的领域模型、仓储或处理器。

频繁读取且要求强一致时，重新判断领域和交付单元边界，或者采用本地投影、事件同步；不得以源码导入绕过错误的服务边界。

## 公开契约

跨边界契约必须满足：

- 字段、错误和语义明确，不直接暴露内部对象。
- 由提供能力的一方或独立协议包维护，并有兼容性策略。
- 不携带数据库连接、框架请求对象、界面组件等运行时内部对象。
- 调用方无需了解提供方的目录、持久化或处理流程。

若契约变更会破坏公开 API，按根 `AGENTS.md` 的安全闸门先取得用户确认。

## 禁止的逃避模式

- 直接导入另一个切片的内部文件。
- 用 `adapter`、`bridge`、`facade` 或 `proxy` 重新导出其他切片或领域的内部实现。
- 把业务调用塞入全局 `shared/`，借技术模块转发。
- 跨交付单元共享某服务的领域模型实现、处理器、仓储或事务流程。
- 依赖隐式全局状态或导入副作用完成注册。

判断转发层是否违规看行为而非名称：若它只重新导出内部实现，没有增加稳定协议，并使调用方继续随提供方内部变化而变化，它就是隐藏耦合。

## 选择流程

1. **识别协作目的：** 技术能力、完成后触发、同步查询或跨进程命令只能选定一种主目的。
2. **选择边界：** 技术能力使用全局基础设施；后续副作用使用事件；同步查询或跨单元能力使用公开协议。
3. **定义契约：** 输入、结果、错误、兼容性所有者和可观察结果明确时完成。
4. **实现两侧：** 双方仅依赖契约；未出现内部导入或重新导出时完成。
5. **显式装配：** 订阅、客户端和具体实现均在组合根连接，组合根无业务判断。
6. **验证：** 生产方、消费方、兼容性以及失败路径均从各自公共入口验证，依赖检查通过时完成。

## 通知与跨交付单元

“发送订单确认”等包含业务语义的通知是独立切片，通用邮件客户端才属于技术共享。跨交付单元只共享公开 Schema、接口描述、生成客户端所需契约及无业务语义技术库；业务流程通过公开协议协作。每个交付单元拥有自己的组合根和启动入口，不共享隐式运行时状态。

## 完成标准

每条跨边界依赖都有明确目的、公开契约、所有者、兼容性策略和组合关系；调用方未接触提供方内部实现，双方的成功与失败行为均已验证。
